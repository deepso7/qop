---
title: API
description: Run the qop API, which sponsors invitation-gated registration and phone-approved device changes.
---

The API checks owner-signed EIP-712 requests and submits them to the registry, paying the gas. It never receives owner secrets or messages, and it can't approve a device on its own. Clients still confirm accounts and devices over RPC.

## Configure

Copy `api/.env.example` to `api/.env` and set:

| Variable | Description |
| --- | --- |
| `DATABASE_URL` | Postgres connection string. |
| `PORT` | Port to listen on. Defaults to `3000`. |
| `RPC_URL` | RPC endpoint for the registry's chain. |
| `CHAIN_ID` | Chain ID of the registry. |
| `REGISTRY_ADDRESS` | Deployed registry address. |
| `REGISTRY_CONFIRMATIONS` | Block confirmations before the API treats a transaction as final. |
| `REGISTRATION_PRIVATE_KEY` | Co-signs gated registrations. Must match the registry's `REGISTRATION_SIGNER`. |
| `RELAYER_PRIVATE_KEY` | Pays gas and submits transactions. Fund it, and keep it separate from the registration key. |

Keeping the two keys separate means the funded relayer can't authorize registrations.

For a local Anvil chain, set `REGISTRY_CONFIRMATIONS=0`. Anvil only mines a block per transaction, so the example's `12` leaves registrations and device actions waiting for blocks that never come.

## Run

```sh
pnpm --filter @qop/api db:push           # create the schema
pnpm --filter @qop/api admission:create  # print an invitation code
pnpm --filter @qop/api dev
```

## Invitation codes

`admission:create` prints a single-use code like `ABC-123`. Give it to the person who will register; the database stores only a hash. The API also accepts lowercase and the compact `ABC123` form.

A code is claimed when a signed registration is stored, consumed when it confirms, and released if the registration fails so the user can try again.

<Callout type="warning">
  The short code format needs request throttling in front of the API before
  public deployment.
</Callout>

## Routes

| Route | Description |
| --- | --- |
| `POST /v1/registrations` | Validate and submit a registration. |
| `GET /v1/registrations/:digest` | Check a registration against the registry, rebroadcasting if needed. |
| `POST /v1/device-actions` | Validate and submit an owner-signed device add or remove. |
| `GET /v1/device-actions/:digest` | Check a device action's receipt and registry event. |
| `GET /openapi.json` | OpenAPI description. |

## Deploy

`pnpm --filter @qop/api build` produces two outputs: `dist/main.mjs`, a Node server, and `.vercel/output`, a prebuilt Vercel deployment.

### Docker

Build from the repository root, then pass the variables from `.env.example` to the container:

```sh
docker build -f api/Dockerfile -t qop-api .
```

### Vercel

- Set **Root Directory** to `api` and keep "Include files outside the root directory" enabled.
- Add the variables from `.env.example` except `PORT`, plus `ENABLE_EXPERIMENTAL_COREPACK=1`.
- For Neon, use the pooled connection string (the `-pooler` host with `sslmode=require`) and put the function in the same region as the database.

`api/README.md` covers the details.
